## Run 1: FAILED at the ISO download

What worked:

- `mtx-pxe` picked up the install job: the boot menu chose the MigraTux install entry.
- The VM got `192.168.117.137` from VMware's DHCP server.
- The installer's boot scripts (casper) started to download `http://192.168.117.136:8080/ubuntu.iso`.

What failed: the download reached 96 % (3755 MB), then:

```
(initramfs) wget: short write: No space left on device
Unable to find a live file system on the network
```

The VM dropped to the BusyBox `(initramfs)` shell.

## Run 2: FAILED the same way, VM set to 12 GB

- The memory of `mtx-pxe` was raised to 12 GB. Same result: `wget` stopped at 3768 MB with `short write: No space left on device`.
- **Not confirmed that the VM really ran with 12 GB.** Going back to the snapshot `pxe-empty` also sets the memory back to the value of the snapshot (8 GB). The RAM inside the VM was not checked (`free -m` at the `(initramfs)` prompt would show it).
- So there are two possible readings, and this run does not decide between them:
  1. the VM had 8 GB again, and the limit depends on the RAM; or
  2. the VM had 12 GB, and the limit is a fixed size.

## Cause

Checked in the source of casper (the boot scripts of the Ubuntu 24.04 installer):

- The boot entry used `url=http://…/ubuntu.iso` (`server/templates/grub.cfg.tmpl`). With `url=`, casper downloads the whole ISO with `wget` into the root of the initramfs and then mounts it.
- The root of the initramfs is a RAM disk. Casper has no parameter for its size.
- `setup.sh` takes the newest 24.04 ISO. Since September 2026 that is 24.04.5 (listed as 3.8G; 24.04.4 was 3.2G). The code and the RAM check (`MIN_RAM_MB=6000` in `server/migratux`) assumed a 3 GB ISO.

Not checked, only a likely explanation: Linux normally limits such a RAM disk to half of the RAM. With 8 GB that is about 3.9 GB minus the installer's own boot files, which fits the 3755 MB of run 1. If run 2 really had 12 GB, this explanation is wrong and the limit is fixed.

**Finding: the ISO-in-RAM boot does not work with the 24.04.5 ISO on 8 GB, and maybe not with more RAM either.** Either way, the RAM a client needs grew with the ISO. That does not fit the goal (old PCs).

## Decision and fix (2026-11-16)

User decision: the installer no longer loads the ISO into RAM. The server unpacks the ISO and exports it read-only over NFS; the boot entry uses `netboot=nfs nfsroot=<SERVER_IP>:/srv/nfsroot`. The server's initrd has what this needs (`nfs.ko.zst`, `usr/bin/nfsmount`, checked on `mtx-server`).

Built the same day (new service `nfs`, `setup.sh` unpacks the ISO, new GRUB line, RAM warning now under 3 GB as an estimate). Automatic tests pass, and the new NFS container was mounted locally with the same `nfsmount` tool the installer uses. **Not tested yet: a real network install over NFS.** That is the next M4 run, with a new result file.
