## Server setup

## Run 1: FAILED, server network adapter hung during the install

What worked:

- `mtx-pxe` showed the boot menu and chose the install entry, then "lade Installer".
- **The NFS mount worked.** `nfs` log: `mountd: authenticated mount request from 192.168.117.137`.
- Subiquity started and partitioned `sda`.

What failed: after about 6 minutes the install froze at the mount step. The console of `mtx-server` showed again and again:

```
e1000 ens37: Detected Tx Unit Hang
```

Cause: VMware's emulated e1000 adapter on the server hung under the NFS load.

### Fix between run 1 and run 2

- Both network adapters of `mtx-server` switched from e1000 to vmxnet3 in the `.vmx` file (`ethernet0.virtualDev` and `ethernet1.virtualDev`).
- The interface was renamed `ens37` → `ens224`. The IP `.136` stayed the same.
- `PXE_INTERFACE=ens224` set in `server/.env`. **That alone was not enough:** the `pxe` container does not read `PXE_INTERFACE` from the environment. It reads `data/conf/dnsmasq.conf`, which `setup.sh` writes. dnsmasq kept logging `interface ens37 does not currently exist` until these two commands were run:
  ```bash
  ./setup.sh --no-build
  docker compose up -d --force-recreate pxe nfs
  ```
  (`nfs` reads `PXE_INTERFACE` at start to find the client subnet, so it needs to be recreated too.)
- Snapshot `server-clean` taken again.

## Run 2: FAILED, the install needs internet

- Boot and NFS fine. No Tx Unit Hang on the server.
- Failed in the postinstall step: `curtin system-install ubuntu-desktop-minimal` ended with exit code 100 (apt), three times.
- Cause: `mtx-pxe` was only on the lab VMnet and had no internet, so apt could not download the desktop packages.
- **This contradicts the project goal of an offline install.** Today the install only works with internet.

## Run 3: OK

- A second, temporary NAT adapter added to `mtx-pxe` for internet.
- The install finished in **about 8 minutes**, measured from the GRUB menu (not from power-on).
- At the end a "failed CD-ROM mount" message showed. It did no harm: the install went on and the VM rebooted. (Likely because the installer's files came from NFS, not from a CD; not checked.)
- After the reboot, `systemd-networkd-wait-online` held up the first boot.
- `migratux-firstboot` ran and exited 1 with "Kein Inventar für diesen PC auf dem Server (MAC 00:0c:29:f2:2f:4d 00:0c:29:f2:2f:57)". **Expected:** this PC has no Windows inventory. It lists both MACs because the client had two adapters.
- **The info screen was not readable:** it went almost straight to the login screen.
- Login screen reached **11:23 min after the GRUB menu** (wait-online delay included).
- Checks: `LANG=de_CH.UTF-8`, X11 layout `ch`, `ssh` and `NetworkManager` `active`, SSH login from `mtx-server` works.

## Run 4 (step 9): OK with 4 GB RAM

- `mtx-pxe` set to **4 GB** memory. Same job and same path as run 3.
- The install completed, the login screen was reached, the client works.
- Time: **about 15-17 minutes, approximate** (not measured exactly).
- The boot phase was noticeably slower than with 8 GB.
- **Finding: 4 GB RAM is enough for the network install over NFS.** It is the lowest value tested; less was not tried. `MIN_RAM_MB=3000` in `server/migratux` (warning in `migratux start`) stays an estimate below that.

## Open items

- **Make the install work offline.** Serve `ubuntu-desktop-minimal` and its dependencies from the server (local package mirror or cache), or leave the package out of the install. Today run 2 shows the install fails without internet.
- **`systemd-networkd-wait-online` delays the first boot.** Find out why and how long. Not checked: the client had two adapters in run 3, and wait-online by default waits for all of them. Probably fix it in the autoinstall config or in `install/mtx-late.sh`.
- **The info screen shows too briefly to read** when first boot fails fast ("Kein Inventar"). It should stay long enough to read, or until a key is pressed (M7 checks the screen).
- **Lab setup: use vmxnet3 on `mtx-server`, not e1000.** Run 1 shows e1000 hangs under NFS load. `docs/lab-setup.md` should say so, and that changing the adapter renames the interface (`PXE_INTERFACE`, then `./setup.sh --no-build` and recreate `pxe` and `nfs`).
- **`migratux status` showed the wrong last state.** The client sent `firstboot`, `connect` and `failed` within the same second (17:16:47 in `m4-compose.log`), but status showed `firstboot`. `last_event` in `server/migratux` takes the newest event file with `sort -n` on the file time; with equal times it falls back to the file path, and `firstboot` comes last in alphabetical order. That fits the observation but is not checked (it needs equal file times). Fix idea: order events by a counter or the time in the event, not by file time.
- The job removal also tried the NAT MAC (`DELETE /pxe/hosts/00:0c:29:f2:2f:57.cfg` → 404). Harmless: the job was on the lab MAC and was removed (204).
- Measure the time from power-on to the login screen (run 3 started at GRUB), ideally without the wait-online delay.
- Optional: find out why the boot phase is slower with 4 GB, and measure run 4's time exactly.
